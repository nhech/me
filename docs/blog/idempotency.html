Why every money-touching endpoint needs idempotency

2026-08-068 MIN READTRỊNH DUY LONG

A retry is not an edge case. It is the normal behaviour of every mobile client on a bad connection, every load balancer with a timeout, and every queue with at-least-once delivery. If your transfer endpoint cannot tell the difference between a new request and a replay, you will move the same money twice.

On the wallet work at Mirailabs this was the first thing we designed, not the last. Below is the shape that survived production.

The contract

The client generates a key and owns it. The server stores the first result against that key and replays it verbatim for any repeat, including the status code.

POST /transfers
Idempotency-Key: 9f2b41ac-...

→ 201  { id: "tr_81", status: "settled" }   first call
→ 201  { id: "tr_81", status: "settled" }   replay, same key
→ 409  { error: "key_reused_with_different_body" }

The 409 matters. If the same key arrives with a different payload, that is a client bug, and silently returning the old result hides it.

Where it actually breaks

Storing the key after the write is the mistake everyone makes once. Two concurrent replays both miss the lookup, both proceed, and you are back where you started. The insert of the key and the write have to land in the same transaction.

If the key and the write are not in one transaction, you do not have idempotency. You have a race that usually wins.

Keys expire. Twenty-four hours covered every legitimate retry we saw; anything older is a new intent, not a replay.
